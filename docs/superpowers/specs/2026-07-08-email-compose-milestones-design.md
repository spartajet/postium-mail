# 发件功能里程碑需求

## 背景

Postium Mail 的发件链路已经从基础 SMTP 投递演进到可用的邮件客户端发件能力：后端会校验正式发送请求，生成 Message-ID，SMTP 成功后写入本地 Sent，并尝试通过 IMAP APPEND 归档到远端 Sent；写信窗口已经支持远端 Drafts 草稿保存、普通本地附件发送、发件账号选择和草稿发送后的清理。

当前下一阶段不应该继续堆叠零散功能，而需要先建立一个发件功能里程碑文档，系统记录还缺哪些用户可感知能力、协议语义能力、可靠性能力和测试保障能力。后续实现应按本文优先级逐阶段推进，每个阶段再单独写详细设计和实施计划。

## 当前基线

已经具备的能力：

1. 正式发送要求至少一个收件人、主题非空、正文非空。
2. SMTP 配置优先使用账号手动配置，缺失时回退 provider 默认配置。
3. 后端生成 Message-ID 和 RFC822 原文，SMTP 投递和 Sent 归档使用同一封邮件。
4. SMTP 成功后写入本地 Sent。
5. SMTP 成功后尝试 IMAP APPEND 到远端 Sent，远端归档失败不引导用户重复发送。
6. 支持远端 Drafts 草稿保存、更新、删除和发送成功后的草稿清理。
7. 支持普通本地文件附件发送，草稿和已发送邮件可保存附件元数据。
8. 所有账号视图下可选择发件账号，回复和转发默认使用原邮件所属账号。
9. 接收侧已经修复 RFC 2231 附件文件名解析，避免接收附件名退化为 `attachment-{id}`。

已知限制：

1. 写信窗口仍使用逗号分隔文本输入收件人，不能逐个展示、编辑和校验地址。
2. 前端没有 BCC 输入界面，后端虽然支持 `bcc` 字段，但当前 UI 一直传空数组。
3. 回复和转发只是预填收件人、主题和正文，没有完整邮件语义。
4. 回复邮件没有设置 `In-Reply-To` 和 `References`，无法可靠进入邮件会话线程。
5. “全部回复”入口存在文案和菜单基础，但未形成完整行为。
6. 转发没有标准转发头，没有明确附件转发策略。
7. 没有签名、Reply-To、发件别名和账号级默认发件配置。
8. 没有发送队列、失败重试、取消发送、后台补偿任务。
9. 附件缺少大小限制、拖拽添加、发送前统一校验和内联图片能力。
10. 草稿失败兜底、关闭确认、并发编辑冲突处理还不完整。

## 优先级原则

后续发件功能优先以“邮件客户端完整度”为主线，同时不牺牲已建立的可靠发送基础。

优先级定义：

1. **P0：语义缺口**。界面已经出现或用户自然会期待，但当前行为不完整的能力。优先处理，避免“看起来支持但实际不正确”。
2. **P1：高频写信能力**。大多数用户日常写邮件都会用到的能力，例如 BCC、收件人输入体验、签名。
3. **P2：可靠性增强**。网络不稳定、服务端异常、大附件耗时等场景下的恢复能力。
4. **P3：高级效率能力**。模板、定时发送、内联图片、复杂富文本等提升效率但不影响基础完整度的能力。

## 里程碑总览

建议按以下阶段推进：

| 里程碑 | 主题 | 优先级 | 目标 |
| --- | --- | --- | --- |
| M1 | 收件人字段与 BCC UI | P0/P1 | 让写信表单具备完整收件人字段和基础地址体验 |
| M2 | 回复、全部回复与转发语义 | P0 | 让现有回复/转发入口符合邮件客户端语义 |
| M3 | 发件身份与签名 | P1 | 支持账号级发件偏好、签名和 Reply-To |
| M4 | 发送队列与失败恢复 | P2 | 处理网络失败、重试、取消和补偿任务 |
| M5 | 附件与富文本增强 | P2/P3 | 完善附件限制、拖拽、内联图片和富文本发送 |
| M6 | 协议兼容与真实邮箱验证 | P2/P3 | 建立跨服务商发件验证矩阵和诊断能力 |

## M1：收件人字段与 BCC UI

### 需求

1. 写信窗口展示 To、Cc、Bcc 三类收件人字段。
2. Bcc 默认可折叠，但用户可以显式展开并输入密送地址。
3. 正式发送时，To、Cc、Bcc 合并后至少存在一个有效地址即可发送。
4. Bcc 地址只进入 SMTP envelope，不应写入最终邮件头。
5. 收件人输入应从逗号分隔文本逐步升级为 token/chip：
   - 支持键入逗号、分号、空格或回车后生成地址 token。
   - 支持粘贴多个地址并自动拆分。
   - 支持逐个删除地址。
   - 支持标记无效地址。
6. 草稿保存应包含 Bcc 字段，重新打开草稿时恢复 Bcc。
7. 前端错误提示应能定位到具体无效地址，而不是只显示泛化发送失败。

### 非目标

1. 本阶段不要求联系人自动补全。
2. 本阶段不要求通讯录。
3. 本阶段不改变后端 SMTP 投递语义，只接通 UI 和校验体验。

### 验收标准

1. 用户可以在 UI 中输入 Bcc 并成功发送。
2. Bcc 不出现在邮件原文头部。
3. 粘贴多个地址后能拆分成多个收件人。
4. 无效地址在发送前或发送失败时能明确提示。

## M2：回复、全部回复与转发语义

### 需求

1. 回复邮件时：
   - 默认收件人为原邮件发件人。
   - 主题使用规范 `Re:` 前缀，避免重复叠加。
   - 正文包含可识别的引用原文区域。
   - 邮件头设置 `In-Reply-To` 和 `References`。
2. 全部回复时：
   - 默认收件人包含原邮件发件人和原邮件收件人。
   - 自动排除当前发件账号自身地址。
   - 原邮件 Cc 进入回复 Cc。
   - Bcc 不参与全部回复。
3. 转发邮件时：
   - 默认收件人为空。
   - 主题使用规范 `Fwd:` 前缀，避免重复叠加。
   - 正文包含标准转发信息块，例如原发件人、日期、收件人、主题。
   - 用户可以选择是否带上原邮件附件。
4. 后端发送请求需要能够表达回复/转发上下文，而不是只依赖前端拼 HTML。
5. 草稿保存需要保留回复/转发上下文，避免草稿发送时丢失线程头。
6. 已发送邮件、本地 Sent 和远端 Sent 应保留相同的回复/转发头部。

### 非目标

1. 本阶段不做复杂会话视图。
2. 本阶段不要求自动合并邮件线程 UI。
3. 本阶段不实现“作为附件转发原邮件 `.eml`”。

### 验收标准

1. 回复邮件能在主流邮箱客户端中进入同一会话线程。
2. 全部回复不会把当前账号自己加入收件人。
3. 转发正文包含清晰原邮件信息。
4. 转发附件策略明确，用户不会误以为附件已转发但实际未发送。

## M3：发件身份与签名

### 需求

1. 支持账号级默认签名。
2. 写信窗口打开时自动插入当前发件账号签名。
3. 切换发件账号时，签名应按账号变化，并避免破坏用户已编辑正文。
4. 回复和转发签名插入位置应符合常见客户端习惯：
   - 新邮件：正文末尾。
   - 回复：用户输入区域下方、引用原文上方。
   - 转发：用户输入区域下方、转发内容上方。
5. 支持 `Reply-To` 配置。
6. 支持发件显示名预览和账号级默认发件名称。
7. 后续可扩展发件别名，但第一阶段可以只做账号主地址。

### 非目标

1. 本阶段不要求签名模板市场。
2. 本阶段不做复杂富文本签名编辑器。
3. 本阶段不做多别名 SMTP 授权校验。

### 验收标准

1. 每个账号可以保存自己的签名。
2. 新建、回复、转发都能正确插入签名。
3. 用户编辑正文后自动保存草稿不会重复插入签名。
4. Reply-To 能写入邮件头并随 Sent/Drafts 保存。

## M4：发送队列与失败恢复

### 需求

1. 正式发送从“点击后等待同步完成”升级为可观察的发送任务。
2. 支持发送中状态展示，包括连接、认证、上传附件、SMTP 投递、Sent 归档、草稿清理。
3. SMTP 投递前失败时保留编辑内容，并允许用户修改后重试。
4. SMTP 投递成功但 Sent APPEND、草稿删除或本地状态更新失败时，不提示用户重复发送。
5. 引入后台补偿任务：
   - 远端 Sent APPEND 失败后可重试归档。
   - 草稿清理失败后可重试删除。
   - 本地状态和远端状态不一致时可给出诊断。
6. 支持用户取消尚未开始 SMTP 投递的发送任务。
7. 同一草稿不应被重复发送。

### 非目标

1. 本阶段不做完全离线发件箱。
2. 本阶段不保证应用退出后所有发送任务继续运行。
3. 本阶段不做定时发送。

### 验收标准

1. 用户可以清楚看到发送处于哪个阶段。
2. 远端归档失败不会导致重复投递。
3. 可重试错误和不可重试错误有明确区分。
4. 自动化测试覆盖 SMTP 成功但后续补偿失败的分支。

## M5：附件与富文本增强

### 需求

1. 发送前校验附件是否仍存在、是否可读、大小是否超过限制。
2. 支持账号或全局附件大小限制，默认值应保守。
3. 写信窗口支持拖拽文件添加附件。
4. 附件列表支持打开、移除、显示大小和类型。
5. 转发原邮件时支持选择是否包含附件。
6. 支持内联图片：
   - 编辑器插入图片后构建 `cid:` 引用。
   - MIME 使用 related/mixed 组合结构。
   - 草稿、Sent 和远端收件客户端都能正确显示。
7. 富文本输出应减少无效 HTML，保证纯文本 fallback 可读。

### 非目标

1. 本阶段不做云附件。
2. 本阶段不做附件压缩或分块上传。
3. 本阶段不做端到端加密附件。

### 验收标准

1. 附件缺失或不可读时不会进入 SMTP 投递。
2. 超限附件有清楚提示。
3. 拖拽添加和按钮添加行为一致。
4. 内联图片在主流邮箱客户端能显示。

## M6：协议兼容与真实邮箱验证

### 需求

1. 建立真实邮箱 opt-in 验证矩阵，覆盖至少以下维度：
   - 163/网易类邮箱。
   - QQ 邮箱。
   - Gmail。
   - Outlook/Microsoft 365。
   - 自定义 IMAP/SMTP。
2. 验证场景包括：
   - 普通发送。
   - 附件发送。
   - Drafts 保存和清理。
   - Sent 归档。
   - 回复线程。
   - Bcc 隐藏。
   - 中文主题、中文正文、中文附件名。
3. 错误日志应包含账号 ID、provider、阶段、Message-ID、远端文件夹和可脱敏错误。
4. 前端错误提示应区分：
   - 参数错误。
   - 认证失败。
   - SMTP 投递失败。
   - 远端归档失败。
   - 草稿保存失败。
   - 附件读取失败。
5. 文档记录各服务商差异和已知限制。

### 非目标

1. 真实邮箱测试不进入默认 CI。
2. 不在日志中记录明文密码、access token 或完整邮件正文。

### 验收标准

1. opt-in 测试能安全跳过未配置账号的环境。
2. 每次协议层修复都能找到对应真实邮箱验证项。
3. 发送失败问题能从日志定位到具体阶段。

## 后续功能池

以下功能暂不进入前六个里程碑，但应保留扩展空间：

1. 定时发送。
2. 发送模板。
3. 联系人自动补全和通讯录。
4. 邮件撤回或延迟发送窗口。
5. S/MIME、PGP 等安全邮件能力。
6. Markdown 写信模式。
7. 多窗口写信。
8. 草稿冲突合并。
9. 发件别名和多身份 SMTP 策略。
10. AI 辅助润色、摘要上下文回复。

## 推荐推进顺序

按当前代码基线，后续建议先做：

1. **M1 收件人字段与 BCC UI**：范围相对清晰，能补齐当前 UI 明显缺口，也为全部回复做基础。
2. **M2 回复、全部回复与转发语义**：解决现有入口语义不完整的问题，是邮件客户端完整度的核心。
3. **M3 发件身份与签名**：提升日常写信体验，和账号设置关联较强，应在回复/转发结构稳定后做。
4. **M4 发送队列与失败恢复**：在发件语义稳定后增强可靠性，避免过早设计队列导致返工。
5. **M5 附件与富文本增强**：普通附件已可用，高级附件和内联图片可以等核心语义完成后推进。
6. **M6 协议兼容与真实邮箱验证**：应贯穿每个阶段，但完整矩阵可以在核心发件能力稳定后系统化。

## 文档使用方式

本文只描述发件功能需求、优先级和里程碑边界，不包含详细实施计划。后续每进入一个里程碑，应单独创建对应的设计文档和实施计划，明确本阶段目标、非目标、接口变更、数据流、测试策略和验收标准。
