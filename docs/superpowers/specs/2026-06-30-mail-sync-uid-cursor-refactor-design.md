# 邮件同步 UID 游标重构设计

日期：2026-06-30

## 背景

当前邮件同步已经引入“首次同步范围”和“加载更早邮件”能力，但真实实现和旧设计文档存在明显偏差：

1. 旧设计要求“同步更久邮件”每次向前回填 3 个月。
2. 当前后端实际使用 `history_before_uid`，每次按 UID 游标向前拉取固定数量邮件。
3. 前端文案仍是“同步更久邮件”，容易让用户理解为按时间窗口同步。
4. `history_synced_since` 和 `history_before_uid` 同时存在，但控制流程主要依赖 UID，状态语义混杂。
5. 增量同步仍有单次只扫描 100 个 UID、统计结果不准确等问题。
6. Full Sync 在某些路径会删除整个文件夹本地数据，和历史回填的幂等追加模型不一致。

本轮重构目标是收敛同步模型，让“新邮件同步”和“旧邮件回填”分别由清晰的 UID 游标控制。

## 目标

1. 历史回填改为明确的 UID 游标分页模型。
2. 每次“加载更早邮件”最多拉取固定数量的更早邮件，默认 50 封。
3. 批量大小使用常量定义，方便后续修改。
4. 历史回填只使用 `history_before_uid` 推进，不再用日期窗口控制下一次查询。
5. `history_synced_since` 仅作为展示或统计字段，不参与控制流程。
6. 前端文案从“同步更久邮件”调整为“加载更早邮件”。
7. 修正增量同步单次只处理 100 个 UID 的限制。
8. 修正增量同步结果统计，让同步完成提示可信。
9. 明确 Full Sync 和历史回填的边界，历史回填不得删除本地文件夹内容。

## 非目标

1. 本轮不做复杂同步队列。
2. 本轮不做多账号、多文件夹后台同步调度重构。
3. 本轮不删除数据库字段 `history_synced_since`。
4. 本轮不重写整个同步调度器。
5. 本轮不改变账号创建前的 IMAP 验证流程。
6. 本轮不实现自动无限滚动远端同步，历史回填仍由用户明确触发。

复杂同步队列、账号级/文件夹级并发锁和后台任务统一调度放到本轮重构之后再设计。

## 推荐方案

采用“高水位 UID 同步新邮件，低水位 UID 回填旧邮件”的模型。

核心规则：

1. `last_sync_uid` 是新邮件同步的高水位游标。
2. `history_before_uid` 是旧邮件回填的低水位游标。
3. `history_exhausted` 表示远端已经没有更早邮件。
4. `history_synced_since` 只记录目前本地看到的最早邮件时间，用于展示和诊断。
5. 首次同步范围继续保留，用户仍可选择最近 1 周、1 个月、3 个月、1 年或全部。
6. 首次同步完成后，按本地最小 UID 初始化 `history_before_uid`，为后续旧邮件回填建立低水位边界。

## 状态语义

### `last_sync_uid`

用于普通同步，只追踪已同步的最高 UID。

普通同步应查询 `last_sync_uid + 1` 之后的远端 UID，并将所有新增 UID 同步到本地。同步成功后，`last_sync_uid` 推进到本批最大 UID。

### `history_before_uid`

用于历史回填，只追踪下一次历史查询的 UID 上界。

历史回填每次查询：

```text
UID 1:(history_before_uid - 1)
```

然后从结果中取最后 `HISTORY_UID_BATCH_SIZE` 个 UID。同步成功后，`history_before_uid` 更新为本批最小 UID。

### `history_exhausted`

以下情况置为 `true`：

1. `history_before_uid <= 1`。
2. 查询 `UID 1:(history_before_uid - 1)` 返回空。
3. 首次同步范围为“全部邮件”且同步成功。

不能因为本批返回数量少于批量大小就直接认为历史耗尽。UID 可能稀疏，服务端文件夹也可能存在删除造成的空洞。

### `history_synced_since`

不参与查询边界计算。

它只表示本地当前看到的最早邮件时间。历史回填保存邮件头后，可以用本批邮件头日期和原值取最小值。它主要用于后续 UI 展示、日志和问题诊断。

## 后端设计

### 批量大小常量

定义历史回填批量大小：

```rust
pub const HISTORY_UID_BATCH_SIZE: usize = 50;
```

如果只在服务层使用，可先放在 `sync_service.rs`。如果测试和其他模块需要复用，放到 `domain::sync` 更合适。

### 历史回填流程

`sync_older_emails(account_id, category)` 流程：

1. 校验分类是否支持历史回填。
2. 根据账号 provider 的文件夹映射，把分类解析为一个或多个 IMAP 文件夹。
3. 对每个文件夹读取 `sync_state`。
4. 计算 `before_uid`：
   - 优先使用 `history_before_uid`。
   - 其次使用当前文件夹本地最小 UID。
   - 再次使用 `sync_state.uidnext`。
   - 都没有时使用 `1`。
5. 如果 `before_uid <= 1`，标记该文件夹 `history_exhausted = true` 并跳过远端查询。
6. 查询 `UID 1:(before_uid - 1)`。
7. 从查询结果中取最后 `HISTORY_UID_BATCH_SIZE` 个 UID。
8. 使用精确 UID 集合拉取邮件头，避免 UID 稀疏时误拉连续范围内的无关邮件。
9. 批量 upsert 邮件头和附件元数据。
10. 拉取并更新邮件正文。
11. 更新 `history_before_uid = min(uid_batch)`。
12. 更新 `history_synced_since` 为本地已知最早邮件时间。
13. 如果远端查询返回空，更新 `history_exhausted = true`。

历史回填永远不调用 Full Sync，也不得删除本地文件夹内容。

### 错误处理

历史游标只在当前文件夹批次完成后推进。

如果 UID 查询失败、邮件头 fetch 失败或邮件头保存失败，不更新 `history_before_uid`，避免跳过未保存的邮件。

如果单封邮件正文拉取失败，可以保留邮件头并继续推进游标。正文失败应记录日志，后续可以通过查看邮件或重新加载单封邮件补齐。

数据库写入需要保持幂等。邮件仍以 `(account_id, folder, uid)` 作为唯一键，重复拉取时 upsert 或忽略重复记录。

### 增量同步修正

普通增量同步当前只查询：

```text
UID (last_sync_uid + 1):(last_sync_uid + 101)
```

这会导致远端一次新增超过 100 个 UID 时，单次刷新同步不完整。

本轮应改为：

```text
UID (last_sync_uid + 1):*
```

或者先查询全部新增 UID，再按批次 fetch。同步成功后，`last_sync_uid` 更新到本批最大 UID。

增量同步应返回真实统计：

1. `new_emails` 为实际新插入邮件数。
2. `updated_emails` 为实际更新邮件数或成功 fetch 的邮件数。
3. 前端完成提示使用真实结果。

### Full Sync 边界

Full Sync 用于首次同步或 UIDVALIDITY 变化，但它和历史回填必须分开。

本轮要求：

1. 历史回填不走 Full Sync。
2. 首次同步范围同步完成后，应初始化 `history_before_uid`。
3. UIDVALIDITY 变化时可以重建文件夹状态，但需要在实现计划中单独处理数据删除风险。
4. 不在普通历史加载路径删除本地邮件。

## 前端设计

### 文案

中文：

```text
加载更早邮件
正在加载更早邮件...
```

英文：

```text
Load older mail
Loading older mail...
```

不再使用“同步更久邮件”。

### 按钮显示规则

邮件列表底部按钮规则：

1. 搜索结果不显示历史回填入口。
2. 星标邮件不显示历史回填入口。
3. 本地分页未加载完时显示“加载更多”。
4. 本地分页已加载完且 `history_exhausted = false` 时显示“加载更早邮件”。
5. 本地为空但历史未耗尽时仍显示“加载更早邮件”。
6. 历史耗尽时不显示按钮，或后续增加轻量结束提示。

### 点击行为

点击“加载更早邮件”后：

1. 调用 `syncStore.syncOlderEmails(accountId, category)`。
2. 成功后刷新当前已加载列表。
3. 保持当前选中邮件。
4. 重新加载当前 `accountId:category` 的历史状态。
5. 如果本批没有新增邮件但历史未耗尽，仍允许用户继续点击。

### 同步状态统一

当前 `EmailState.refreshCurrentCategory` 会直接调用后端 `syncAccount` 命令，绕过 `SyncState` 的同步状态和进度事件。

本轮应把刷新入口收敛到 `SyncState`：

1. 由组件或调用方先调用 `syncStore.syncAccount(accountId)`。
2. 再调用 `emailState.loadEmailsByCategory(...)` 刷新列表。
3. `SyncState` 统一维护 `syncing`、`progress`、`error` 和 Toast。

## 测试设计

### 后端测试

需要覆盖：

1. `history_before_uid` 为空时，用本地最小 UID 初始化。
2. 本地为空时，用 `uidnext` 初始化。
3. `before_uid <= 1` 时标记历史耗尽。
4. UID 查询返回空时标记历史耗尽。
5. 拉到 UID 批次后，游标推进到本批最小 UID。
6. 本批少于 50 封但非空时，不自动标记耗尽。
7. 邮件头保存失败时，不推进历史游标。
8. 增量同步能够处理超过 100 个新增 UID。
9. 增量同步返回真实统计。

### 前端测试

需要覆盖：

1. 本地未加载完时显示“加载更多”。
2. 本地加载完且历史未耗尽时显示“加载更早邮件”。
3. 搜索结果不显示历史回填入口。
4. 星标邮件不显示历史回填入口。
5. 空列表但历史未耗尽时显示“加载更早邮件”。
6. 点击后调用 `syncOlderEmails` 并刷新当前列表。
7. 中文和英文文案更新。
8. 普通刷新通过统一同步状态入口执行。

## 方案取舍

### 方案 A：固定数量 UID 游标分页

优点：

1. 行为稳定，容易解释和测试。
2. 不受邮件日期乱序影响。
3. 避免时间窗口空转。
4. 与当前实现接近，重构风险较低。

缺点：

1. 每次加载的时间跨度不固定。
2. 用户不能直接按月份控制历史范围。

结论：采用。

### 方案 B：三个月日期窗口

优点：

1. 用户语义直观。
2. 可以明确表达“同步到某个时间”。

缺点：

1. 邮件少的文件夹会频繁空转。
2. 邮件日期乱序和服务器日期搜索差异会带来边界问题。
3. 当前代码已经偏向 UID 游标，实现回退成本更高。

结论：不采用。

### 方案 C：自动根据邮箱密度动态决定批量

优点：

1. 可以兼顾列表填充速度和网络成本。
2. 用户体验可能更平滑。

缺点：

1. 规则复杂。
2. 更难测试。
3. 容易和后续复杂同步队列耦合。

结论：不在本轮采用，可作为后续优化。
