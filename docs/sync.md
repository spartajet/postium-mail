### 核心原则
1.  **服务器为准原则**：任何同步冲突，以服务器当前状态为准。
2.  **UID 追踪原则**：必须依赖 IMAP UID 而非序号进行邮件定位。
3.  **元数据驱动原则**：利用 `UIDVALIDITY`、`UIDNEXT`、`HIGHESTMODSEQ` 实现增量同步，避免全量扫描。
4.  **懒加载原则**：先同步信头，后同步正文，按需下载附件。
---
### 场景一：账号添加后的首次同步
**目标**：以最快速度让用户看到邮件列表，避免长时间等待。
**逻辑流程**：
1.  **建立连接与文件夹发现**
    *   连接 IMAP 服务器。
    *   执行 `LIST "" "*"` 获取文件夹树。
    *   **识别系统文件夹**：优先读取 `ATTRIBUTES`（如 `\Sent`、`\Drafts`），若无属性则根据名称猜测（如 "Sent"、"已发送"）。
    *   在本地数据库初始化文件夹结构。
2.  **关键元数据获取**
    *   对每个文件夹执行 `SELECT` 或 `STATUS`。
    *   获取并存储三个关键值：
        *   `UIDVALIDITY`（UID 有效性戳）。
        *   `UIDNEXT`（下一封邮件的 UID 预期值）。
        *   `HIGHESTMODSEQ`（最高修改序列号，用于后续增量同步）。
3.  **快速列表同步（骨架同步）**
    *   **只拉取信头**：执行 `UID FETCH 1:* (FLAGS BODY.PEEK[HEADER.FIELDS (SUBJECT FROM DATE)])`。
    *   **不下载正文**：此时本地数据库已存有邮件列表，用户可以看到发件人、主题、时间。
    *   **记录断点**：记录当前同步到的 UID 位置。
4.  **后台填充（内容同步）**
    *   在用户浏览列表的同时，后台静默拉取最近 N 封邮件（如最近 100 封）的正文（`BODY[]`）。
    *   更旧的邮件仅在用户点击查看时触发实时下载，下载后缓存到本地。

### 场景二：应用启动后的现有账号同步
**目标**：快速修正本地状态，同步离线期间的变更，处理多端冲突。
**逻辑流程**：
1.  **上传本地离线操作（解决冲突第一步）**
    *   检查本地“待上传操作队列”（用户离线时的删除、移位、标记已读操作）。
    *   逐一尝试在服务器执行：
        *   **成功**：从队列移除，更新本地状态。
        *   **失败（邮件不存在）**：说明该邮件已在其他客户端被删除。放弃该操作，并在本地同步阶段处理删除。
        *   **失败（文件夹不存在）**：提示用户或忽略。
2.  **元数据校验（灾难恢复检查）**
    *   对比本地存储的 `UIDVALIDITY` 与服务器当前值。
    *   **如果不一致**：说明服务器重建了邮箱，UID 体系已崩塌。执行**毁灭性重建**——清空该文件夹本地数据，重新执行“首次同步”逻辑。
3.  **增量拉取新邮件**
    *   对比本地 `UIDNEXT` 与服务器当前 `UIDNEXT`。
    *   若服务器值更大，说明有新邮件到达。
    *   执行 `UID FETCH <本地UIDNEXT>:* (FLAGS BODY.PEEK[HEADER...])` 拉取新邮件信头。
4.  **同步状态变更（处理多客户端修改）**
    *   **理想情况（支持 CONDSTORE 扩展）**：
        *   利用 `HIGHESTMODSEQ`。执行 `UID FETCH 1:* (FLAGS) (CHANGEDSINCE <本地MODSEQ>)`。
        *   服务器仅返回自上次同步后状态发生变化的邮件（如其他客户端已读、删除、标记星标）。
        *   批量更新本地数据库的 Flags。
    *   **兜底情况（不支持 CONDSTORE）**：
        *   仅对本地已有的邮件（或最近 500 封）执行 `UID FETCH ... (FLAGS)`。
        *   对比差异：若服务器显示已读，本地未读 -> 更新为已读；若服务器邮件消失 -> 本地删除。

### 场景三：应用在后台时定时获取新邮件
**目标**：在系统限制下感知新邮件，通知用户，保持数据新鲜度。
**逻辑流程**：
1.  **前台策略（应用打开时）**
    *   **使用 IDLE 模式**：对 `INBOX` 发送 `IDLE` 命令，保持 TCP 长连接。
    *   **推送式响应**：服务器一旦有新邮件，主动推送 `EXISTS` 消息。
    *   客户端收到推送后，立即结束 IDLE，执行“增量拉取新邮件”逻辑，随后重新进入 IDLE。
2.  **后台策略（应用切后台/息屏）**
    *   **系统级推送优先**：如果服务提供商支持（如 Gmail、Outlook API），接入系统级推送，这是最省电方案。
    *   **IMAP 轮询兜底**：
        *   利用移动操作系统的后台任务调度器（如 Android WorkManager / iOS Background Fetch），设置间隔（如 15 分钟）。
        *   唤醒后，仅执行轻量级 `STATUS INBOX (UNSEEN)` 命令。
        *   **判断逻辑**：对比服务器返回的 `UNSEEN` 数量与本地数据库。
            *   若数量增加 -> 拉取新邮件头信息 -> 发送本地系统通知。
            *   若数量减少 -> 说明其他端已读，不同步内容，仅更新角标数字。

### 场景四：多客户端情况下的冲突处理
这是同步逻辑中最棘手的部分，核心逻辑是 **"服务器状态覆盖本地"**。
**冲突类型与处理逻辑**：
1.  **状态冲突（已读/未读/星标）**
    *   *现象*：本地显示未读，服务器显示已读（用户在电脑上看了）。
    *   *逻辑*：在“启动同步”阶段，服务器返回的状态直接覆盖本地。本地不保留“已读状态”的上传冲突权，只服从服务器。
2.  **删除冲突**
    *   *现象*：本地有邮件 A，但服务器上邮件 A 已不存在（被其他客户端删除）。
    *   *逻辑*：同步时发现 UID 丢失，直接删除本地邮件，不进入回收站，视为同步操作。
    *   *离线删除冲突*：用户离线删除了邮件 A，上线同步时发现邮件 A 已经被其他端移到了垃圾箱。
        *   *处理*：本地删除操作失败，放弃该操作，同步服务器现状（邮件出现在垃圾箱）。
3.  **移动冲突**
    *   *现象*：用户在手机上将邮件从 A 移到 B，同时在电脑上将同一邮件从 A 移到 C。
    *   *逻辑*：取决于谁先上传成功。后上传者会收到“邮件不存在于 A”的错误。客户端捕获错误后，放弃操作并同步服务器最新位置。
4.  **UIDVALIDITY 变更（毁灭性冲突）**
    *   *现象*：服务器重建或迁移导致 `UIDVALIDITY` 变化。
    *   *逻辑*：视为全新账号。保留本地旧数据（以防用户需要离线查看历史），但标记为“旧存档”，并在后台开启全新的全量同步流程。
---
### 总结：同步逻辑状态机
可以将每个文件夹的同步看作一个状态机：
1.  **初始化状态**：执行全量拉取（头信息），保存 UIDVALIDITY/UIDNEXT。
2.  **稳态运行**：
    *   监听 IDLE 或 定时轮询。
    *   触发变更 -> 增量拉取 -> 更新本地。
3.  **冲突检测**：
    *   检查 UIDVALIDITY -> 变则回退至初始化状态。
    *   检查 MODSEQ -> 变则更新 Flags。
通过这套逻辑，你的应用可以在保证数据准确性的前提下，最大程度减少流量消耗和服务器压力，并能优雅地处理多端操作带来的数据冲突。
